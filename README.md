# Local Reading Assistant

Windows上で正規に表示されている本の画面だけを、ローカルVision LLMへページ順に読ませるデスクトップアプリです。OCR全文を集める道具ではなく、途中の予想・驚き・人物への印象・解釈修正を失わず、一冊を読み終えたAIとして感想を残すことを目的にしています。

## まず起動するファイル

**`start.bat` をダブルクリック**してください。この作業フォルダーには署名済みCPython 3.12.10の必要コンポーネントとPillowを `runtime` に同梱しているため、このPCではPythonの追加導入や初回ダウンロードなしで起動します。システムPATH、ファイル関連付け、Pythonランチャーは変更しません。

GitHubリポジトリでは依存パッケージとビルド済みランタイムを管理しないため、`runtime` は含まれません。GitHubからcloneした環境ではPython 3.10以降をインストールしてから `start.bat` を実行してください。初回のみプロジェクト専用の `.venv` を作成し、`requirements.txt` の依存関係を導入します。

コンソール付きでエラーを確認したいときは `start_debug.bat` を使います。`runtime` を削除した場合だけ、`start.bat` は既存Pythonを探して専用 `.venv` を作るフォールバックになります。

## Qwen / Ollamaの準備

既定値は次のとおりです。

- Base URL: `http://127.0.0.1:11434/v1`
- Model: `qwen3.5:9b`
- ページ最大出力: 1200 tokens（旧版の900は起動時に安全値へ更新）

Ollamaを使う場合は、先にOllamaを起動しておきます。モデルがなければ別途 `ollama pull qwen3.5:9b` が必要です。本アプリはモデルを勝手に導入・更新・停止しません。Ollamaの一般的な4096コンテキストでは、QwenがThinkingだけで残り枠を使い切りJSON本文が空になる場合があるため、既定の `auto` はThinking OFFで安全な階層マルチパスを使います。十分に大きいコンテキストを別途設定した環境では、設定画面から明示的にThinking ONを選べます。他のOpenAI互換サーバーには、未確認の独自パラメータを送りません。

## 基本の使い方

1. Kindle等の正規アプリで本を開き、最初に読むページを表示します。
2. Local Reading Assistantで本の名前と総ページ数を入れ、`新規セッション`を押します。
3. `対象ウィンドウ`を選び、`本文領域を選択`を押します。対象があるモニターの左半分に選択画面が出るので、その中で本文だけを自由に囲みます。
4. Base URLとModelを確認し、`接続確認`を押します。
5. 見開き、読書順、品質、チャンク数を設定し、`設定を保存`します。
6. `10ページ校正を開始`後、10ページを通常どおり読ませて速度と認識品質を確認します。
7. `開始`を押します。
8. 半自動なら`次のページ`、手動なら自分で対象アプリのページを送り`このページを読む`を押します。
9. 章末まで読んだら`ここで章のおわり`を押します。章感想を保存し、次章用の最小記憶へ切り替えます。
10. 中断するときは`一時停止`または`停止`。ページごとにSQLiteへ保存済みです。
11. 最後に`読書終了`を押すと、最後の未確定章も自動で閉じ、4段階の検証後に7ファイルを生成します。

手動モードでは、対象アプリ側でページを送った後に `Ctrl+Shift+R` でも読めます。無人で全ページを自動操作する機能はありません。

本アプリを画面右半分、Kindleやブラウザを左半分へ並べる使い方に対応しています。右半分幅でも上部の`対象ウィンドウ`欄は省略されません。対象一覧から左側のKindleまたはブラウザを選び、`本文領域を選択`を押してください。

最終レポート生成を使わず章メモを別AIへ渡す場合は、対象セッションを再開してから`章メモのフォルダーを開く`を押します。章別Markdownを個別に確認・添付できます。`ChatGPT用に1ファイルへまとめる`を押すと、各章メモを読書順に、本文を変更せずMarkdown区切りだけ加えて`all_chapter_notes_for_chatgpt.md`へ結合し、そのファイルを開きます。外部への自動送信はしません。

## 保存するもの / 保存しないもの

保存するのは、モデルが作った意味要約、人物・心理・関係性、伏線、疑問、途中予想、解釈更新、ユーザーメモ、confidence、perceptual hashだけです。

保存しないもの:

- ページ画像、スクリーンショット、一時JPEG
- OCR全文、本文、本文を再構成できる大量テキスト
- Kindle/ebook内部データ
- API key

画像はページ処理中だけメモリに置き、LLM入力とプレビューが終わると閉じます。データベース保存層でも `ocr_text`、`raw_text`、`transcription`、画像/bytes等を拒否します。モデルが長文転記を始めた場合も応答を保存せず停止します。

保存先:

- 記憶DB: `%LOCALAPPDATA%\LocalReadingAssistant\reading_memory.sqlite3`
- 設定: `%LOCALAPPDATA%\LocalReadingAssistant\config.json`
- レポート: `%LOCALAPPDATA%\LocalReadingAssistant\reports\<本名>_session_<番号>\`
- 章ごとの感想: 上記フォルダ内の `chapter_notes\chapter_XXX_pages_A-B.md`

## 章区切りと記憶リセット

`ここで章のおわり`を押すと、前回の章区切り以降に残っているページをチャンク統合し、次の内容をSQLiteと章Markdownへ保存します。

- 300〜800文字を目安にした、事実中心の章詳細要約
- 場所・人物・行動・重要発言の意味・結果を含む出来事タイムライン
- この章で新しく判明した事実と、新しく生じた伏線だけ
- 人物の具体的な行動、根拠場面付きの感情、実際に変化した関係性
- 新規/継続を分けた未解決事項と、IDを引き継いだ解決事項
- 最大3件の印象的な場面と感情的インパクト
- FACTと推測を分離した限定的な考察・予想
- 読み取り不能または情報不足だったページ位置

保存後は、次のページ読解へ渡す作業コンテキストから前章のページ要約とチャンク詳細を外します。次章へ持ち越すのは、現在重要な人物、未解決の伏線・疑問、章末の具体的状況だけです。テーマ、長い既出説明、予想の再掲は引き継ぎへ入れません。ページメモやチャンクをSQLiteから削除する処理ではありません。アプリを終了して再開しても同じ章チェックポイントを読み戻します。

内部DBでは人物・出来事・関係性・伏線・疑問へ `character_001`、`event_001`、`relationship_001`、`clue_001`、`question_001` のようなセッション内安定IDを割り当てます。`semantic_entity`に現在状態、`semantic_entity_history`にチャンク/章ごとの変更履歴を保存します。同じ疑問を毎章新規登録せず、判明時は同じIDを`resolved`へ更新します。既存DBは起動時にテーブルが自動追加され、以前の章Markdownや要約も読み込み可能です。

## 生成レポート

- `01_summary.md`: 詳細な全巻あらすじ
- `02_characters.md`: 心理・行動・関係性の変遷
- `03_mysteries.md`: 伏線、違和感、回収、未回収
- `04_reading_journey.md`: 途中予想、驚き、外れ、解釈修正
- `05_final_review.md`: 長めの感想・批評
- `06_evidence_check.md`: 解釈、読書メモ上の根拠、確信度、別解釈
- `handoff_for_chatgpt.md`: 別AIと深いネタバレ感想会をするための高密度な引き継ぎ

最終生成は、(1)全巻事実記録、(2)人物・関係・伏線・テーマ統合、(3)捏造/矛盾/事実混同の独立監査、(4)修正版から執筆、の順です。

ページ数の増加でプロンプトが無制限に大きくならないよう、Vision用の直近記憶には固定上限があります。20ページ統合と最終4パスは、大きな素材を時系列順の小グループへ分け、各結果をさらに上位で統合する階層方式です。すべてのLLM入力は送信前に保守的なトークン推定を行い、予算超過時はサーバーへ送信しません。JSON文字列を途中で切る処理はありません。完全な意味メモはSQLiteに残り、圧縮されるのは各LLM呼び出し用の一時的な投影だけです。

VisionページJSONは、人物最大4人、出来事最大4件、その他の主要配列最大3件、要約180文字というOllama構造化出力スキーマで生成します。出来事、新事実、重要発言、人物行動、関係変化、感情・考察の順で情報を優先します。読み取れない場合は前章から補完せず、`UNREADABLE`または`PARTIAL`と不足内容を保存します。情報量の多いページでもJSONを閉じる出力枠を残し、解析失敗時はtemperatureを0へ下げて自動再試行します。

300ページでは既定20ページごとに15チャンクを保持します。`01_summary`、`02_characters`、`03_mysteries`、`06_evidence_check`、`handoff_for_chatgpt`は最大60ページ単位、特に重要な`04_reading_journey`は最大40ページ単位で詳細パートを書き、最後に1ファイルへ結合します。そのため、全巻を一度だけ短く要約する方式と異なり、序盤・中盤・終盤の出来事や途中予想が最終出力へ残ります。`05_final_review`は検証済み全体記憶から一貫した総評として生成します。

最終生成の各検証Passと各レポートパートは、読書メモのハッシュごとに `.generation_cache` へ保存されます。途中でLLMが停止しても、同じ読書メモで`読書終了`をやり直せば完了済み部分を再利用します。キャッシュにも原文や画像は含まれず、LLMが生成した意味メモだけが入ります。

Ollamaが4096コンテキストで動作している場合でもJSONの閉じ括弧まで出せるよう、最終Passの入力は最大1600推定tokens、レポート入力は最大1250推定tokensへ階層分割します。Pass 4はPass 1/2を大量に複製せず、監査で必要になった修正・除外・不確実性を固定JSONスキーマで保存します。各範囲レポートも固定スキーマと文字数上限を使い、詳細さは範囲別ファイル結合によって確保します。

## 事故防止と制約

- 取得するのは、デスクトップ上に現在見えている矩形の通常スクリーンショットだけです。
- 黒画面・単色画面を検出したら、キャプチャ保護を回避せず停止します。
- 対象ウィンドウが他のウィンドウに隠れると、その重なりも画面として写ります。本文領域は見える状態にしてください。
- `本文領域を選択`のオーバーレイは、対象ウィンドウがあるモニターの左半分全体を覆います。その中を自由にドラッグでき、選択結果は対象ウィンドウと重なる範囲へ安全に収めます。対象が右半分にしかない場合は、対象を左側へ移動するか最大化してから選択してください。アプリ側は最大化を解除せず、前面化完了後の最新座標を取り直します。
- 半自動ページ送りは対象ウィンドウを前面化し、通常のRight/Left/PageDown等を1回だけ送ります。内部APIやDOMは使いません。
- ページ送り後は固定待機ではなく、perceptual hashの変化と連続安定を確認します。同一/未切替ページはカウントしません。
- `自動判定`の見開きは画面比率と中央ガターによる保守的ヒューリスティックです。縦書きや特殊レイアウトでは明示設定を使ってください。
- 初期版に無人連続操作はありません。
- localhost以外のBase URLは、画像やメモが外部送信される危険があるため接続を拒否します。クラウドへの自動フォールバックもありません。
- DRM解除、ebook変換、Kindleファイル/内部データ読み取り、キャプチャ保護回避は実装していません。

## 自作サンプルで試す

実在の本は同梱していません。`samples/generated`には、このプロジェクト用に書いた短編『灯台の止まった時計』の10ページ画像があります。再生成する場合:

```powershell
runtime\python.exe tools\generate_sample_book.py
```

最も簡単なのは **`start_sample_reader.bat` をダブルクリック**する方法です。コマンドで起動する場合:

```powershell
runtime\python.exe tools\sample_reader.py
```

このウィンドウを対象にし、画像の内側を本文領域として選択します。左右矢印でページが変わります。

## テスト

```powershell
runtime\python.exe -m unittest discover -s tests -v
runtime\python.exe -m reading_assistant --smoke-test
```

テストは自作画像と模擬ローカルLLMだけを使い、20ページ読解、重複検出、チャンク統合、SQLite中断再開、7レポート生成を確認します。300ページ専用テストでは137ページでアプリ終了相当のDB再接続を行い、300ページ、15チャンク、最大60/40ページ単位の範囲別レポート、最終生成のチェックポイント再開まで検証します。さらに600ページ・30チャンク相当の長大な疑似メモでも、全LLM入力が予算内に収まり7レポートまで完走することを確認します。

## 構成

```text
reading_assistant/
  ui.py                 1画面GUI
  capture/              交換可能な画面取得境界 + Windows実装
  window_control.py     通常キーによるページ送り
  duplicate.py          pHash、黒画面、見開き分割
  llm_client.py         localhost限定 OpenAI互換/Ollamaクライアント
  context_budget.py     トークン予算、完全JSON投影、階層バッチ分割
  analyzer.py           ページVision読解
  integrator.py         約20ページごとの深い統合
  chapter.py            手動章区切り、章感想、最小引き継ぎ
  memory.py             原文を持たないSQLite長期記憶
  reports.py            4パス検証とMarkdown生成
  calibration.py        10ページ速度・品質測定
  orchestrator.py       安全な状態機械と処理順序
```

画面取得は `FrameSource` Protocolに依存しており、将来のChrome版を追加してもLLM・記憶・読書ロジックを変更しない構造です。

詳しい安全境界は `docs/ARCHITECTURE.md`、実行済み検証は `docs/VERIFICATION.md`、同梱Pythonの由来は `RUNTIME_PROVENANCE.md` にあります。
